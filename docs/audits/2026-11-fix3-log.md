### Render verified for real, not just unit-tested
The reel renderer was actually executed here (HyperFrames + Chromium + FFmpeg), which earlier rounds
could not do:

- Output: **1080×1920, h264, 8.0 s** — shape, codec, duration and size all pass `reel-qa`.
- The vendored gsap demonstrably **executes**: the same composition with the script tag stripped
  renders 0 s of black (everything static and visible), against 3.3 s with it (content animating in).
- The vendored fonts demonstrably **load**: black share fell from 3.8 s (fallback fonts, no network)
  to 3.3 s (real Playfair/Inter), and a frame grab shows Playfair Display italic in the headline, the
  gold hero number, Inter body text and the config-driven tagline in the footer.

### One thing that render turned up — reported, not changed
`reel-qa` rejected both renders on its **black-share gate**: 3.3 s of 8.0 s is 41%, over
`maxBlackShare: 0.4`. The cause is structural, not a fault in this branch: the brand background is
`#09090B` (near-black), `blackdetect` runs at `pix_th=0.10`, and the gsap timeline fades the last
element in at 3.8 s, so frames read as black for the whole intro. `renderReel` throws on a QA
failure, so if a Mac render measures the same, **no Instagram Reel can publish at all** — a possible
regression from `85930fd`, which added the gate without the runtime being executed.

Not changed, deliberately: the threshold is a publish-quality judgement, loosening it could let a
genuinely broken reel through, and this measurement is Linux font rasterisation — macOS antialiasing
may well land under 40%. **Action for Tim:** run one render on the Mac and read the black share. If
it also fails, the principled fix is to measure black *after* the intro window (the gate's intent is
"catch an empty or broken render", not "catch a deliberate fade-in"), not simply to raise the number.
