# bpa-social — Beyond Paradise Adventures social pipeline

Weekly: BPI briefs (last 7 days) → ≤3 deterministic drafts ($0; BPI already wrote the prose) →
brand + voice-lint gate → `queue.json` (pending) → WhatsApp message → Tim replies `bpa approve B1`
→ scheduled Facebook Page post (09:00 EAT, one per day) → worker reconciles → posted.

| Piece | Runs as | Notes |
|---|---|---|
| `draft.js` | launchd `com.beyondparadise.bpa-draft` Mon 07:00 | `--dry-run` prints without saving/sending |
| `approval-server.js` | launchd `com.beyondparadise.bpa-approval` KeepAlive, 127.0.0.1:3028 | bridge routes any `bpa …` WhatsApp message here |
| `worker.js` | launchd `com.beyondparadise.bpa-worker` every 15 min | reconcile with Meta, expire 7-day-old drafts, alerts (6 h dedupe), Monday heartbeat |

Commands (WhatsApp self-chat): `bpa` · `bpa approve B1 B2` · `bpa skip B1` · `bpa edit B1: text` ·
`bpa post B1 now` · `bpa approve B1 again` · `bpa post B1 now again` (only after "check Meta first", see the review page notes below) · `bpa status` · `bpa help`. Nothing is ever posted without an explicit approve.
Links are enabled (`includeLinks: true`) — the gate existed only until the site went live on
2026-09-14. A test asserts this line and `config.json` agree, so the two cannot drift again.
Instagram: each approved post is rendered as an 8-second **Reel** (`video.js` → HyperFrames, headless
Chrome + FFmpeg, CPU-only, ~15–60 s) in the brand tokens, hosted via the padelrevive.com media
library, published by the worker at the scheduled time (IG has no API scheduling). `instagram.format`
`"image"` falls back to the static Pillow card (`card.py`). Enable with `instagram.enabled=true` in `config.json` once `instagram_content_publish`
is granted (re-run `meta-pages/connect.js`). Logs: `~/Library/Logs/beyondparadise/social.log`.
Meta access: `shared_knowledge/scripts/meta-pages` (tokens in `~/.config/meta-pages/`).
`igEnabled()` needs `instagram_content_publish` in `user.scopes` of that tokens file (written by `connect.js --exchange`; `connect.js --refresh-scopes` re-reads it from Meta without a new login). If `instagram.enabled` is true but that is missing, the worker (`igGate` in `lib.js`) logs one `… instagram NOT published, Facebook only: <reason>` line per affected post and sends ONE WhatsApp alert per state change (blocked, then back on) — state in `queue.json` → `state.igGate`. It no longer skips quietly.

## Safety switches, cap and health alarm
Config keys in `config.json` (all optional; the defaults below apply when the key is absent):

| Key | Default | What |
|---|---|---|
| `maxInstagramPostsPerDay` | `1` | most Instagram publishes per East Africa Time calendar day; `0` = none; anything but a whole number >= 0 counts as 0 (fail closed). Counted from the ledger below. |
| `autoPublish` | absent (false): **off**, nothing in this pipeline publishes automatically | THE switch of the automatic lane (see "Automatic lane" below). Only the boolean `true` turns it on; anything else is off, the lane's code is not even loaded and nothing is read. Also read by the health check: the "no post for N days" alarm exists only while this is true. Do not turn it on without the owner. |
| `autoKinds` | `["rule", "fact"]` | idea kinds the automatic lane may use. Anything but a non-empty list of names refuses the lane (reason `bad-config:autoKinds`); it is never widened by a typo. |
| `autoSlotHourEAT` | `18` | East Africa hour of the day (0 to 23) at which the day's automatic post is queued to go out; on the next day when that hour has already passed. Anything else counts as 18. |
| `autoRequireApprovedHook` | absent or `false`: **off** | A RESTRICTION, so a typo must not switch it off: `true` = the automatic lane refuses every idea that has no approved, current hand-written hook in `auto-hooks.json` (reason `no-approved-hook`); absent or `false` = an idea without one uses its cut title as hook; ANY other present value (the string "true", 1, null ...) refuses the lane (`bad-config:autoRequireApprovedHook`), like `autoKinds`. Not set in `config.json`. |
| `alarmNoPostDays` | `4` | days before the "no post" alarm, used only when `autoPublish` is true (so today: not active). The clock runs from the LATEST of: the worker first seeing the lane on (`bpa-social-armed.json`), the last successful post, the last worker run that found the pipeline stopped. So switching on, or lifting a long `bpa stop`, never alarms at once; switching off and on again starts a new clock. |
| `ideaDrafts` | absent (false): **off** | switch for drafts from the post-idea pool (`ideas.js`), written by a LOCAL model. Only the boolean `true` turns it on; anything else is off and the new code is not even loaded. Do not turn it on without the owner. |
| `ideaDraftsPerRun` | `3` | most ideas drafted per weekly run (the top ones not yet in the queue); anything but a whole number >= 1 drafts none (fail closed) |
| `captionModel` | the model in `config.json` (code default `hermes3:8b` when the key is absent) | the local Ollama model that writes hook, caption and alt text |
| `judgeModel` | the model in `config.json` (code default `hermes3:8b` when the key is absent) | the local Ollama model that judges each idea draft sentence by sentence (see the judge section; the choice comes from `node judge.js --calibrate`) |
| `judgeMode` | absent = `"shadow"` | `"off"`: the judge is not run. `"shadow"`: every idea draft that passed its checks is judged, the verdict is stored on the draft (`judge`) and one line (ids, verdict, check ids; no caption text) is appended to the private file `bpa-judge-shadow.jsonl` in the state folder; the draft is queued as before. `"enforce"`: a draft the judge fails is not queued and is logged with its check ids. Any other value is treated as `"enforce"` (a typo must not turn the filter into advice). Only matters while `ideaDrafts` is on. |

Files (folder `~/.matlai/`, override `BPA_STATE_DIR`): `bpa-social-stop` (stop flag; `BPA_STOP_FLAG`; `bpa stop` creates it, `bpa start` removes it; the fleet `stop-all.flag`, `STOP_ALL_FLAG_PATH`, also stops), `bpa-social-ig-ledger.jsonl` (`BPA_LEDGER_PATH`), `bpa-social-run.json`, `bpa-social-lastpost.json`, `bpa-social-alerts.json`. Log path override: `BPA_LOG_PATH` (tests set it; see `test-env.js`).
`bpa stop` does not cancel Facebook posts already scheduled at Meta; the reply says how many and when.
Health: `node health.js --check` exits 1 when the worker has not run for 45 minutes (`worker-stale`) or runs but fails (`worker-failing`: last result is an error, or no successful run for 45 minutes). The approval server runs the same check hourly and sends one WhatsApp alert per condition per 24 hours; for 20 minutes after it starts, a missing or old worker state is treated as unknown.

## Idea drafts and the local model (`caption.js`, `local-model.js`, `idea-drafts.js`)
Free and local only: `local-model.js` is the one caller and it can only reach Ollama on `127.0.0.1` / `localhost` port 11434 (any other host throws before a request is built). Before every request it refuses on: the stop flag (own or fleet-wide), the per-run cap (120 calls), the per-East-Africa-day cap (1,500) from the counter file `bpa-segments-calls.json` in the state folder (`BPA_SEGMENTS_COUNTER` overrides; the same file the media segment step uses (media-segments.js now calls `askLocal` too: one guard, one counter, one lock), reserved BEFORE the call, an unreadable counter refuses). Per call: 120 s timeout, `keep_alive` 2m, a large `num_predict`; an empty answer is a failure.
`caption.js` `draftFromIdea` gives the model only an idea's title and claim texts and takes back `{ hook, caption, altText }`. Code adds the source line, a pointer line (only for a path on our own site) and hashtags from a fixed vocabulary. Checks, each with a named reason: `not-json`, length limits, `number-not-in-claims`, `url-in-text`, `mention-in-text`, `hashtag-in-text`, `voice-lint`, `rules:<id>`; two retries, then the idea is given up. With `ideaDrafts` on, `draft.js` queues the results through the same gates, states and approval prompt as the weekly drafts (kind `idea`, Instagram format carousel via `formatByKind.idea`).
`node caption.js --bakeoff --ideas 10 --models a,b,c [--out file]` compares installed local models on the real pool (one model at a time, unloaded after, skipped under 15 percent free memory).

## The draft judge (`judge.js`)
`judgeDraft(draft, { ask, model, now })` answers `{ verdict: "pass" | "fail", reasons: [{ check, detail }], model, seconds, at }`. Order, cheap first, and a fail anywhere stops the later steps: (1) no model: the draft has claims, the final check (voice + rules) passes, number fidelity (every figure of the hook, caption and alt text is in a claim), no empty praise or filler (`FILLER_PHRASES`, check id `filler`); (2) by model, one closed question per model-written sentence (hook and caption; never the source line, the pointer or the hashtags) with the claim texts as the facts: does the sentence state anything the facts do not (event, cause, judgement, recommendation, time, place, actor, a figure attached to the wrong thing)? `{ "supported": true | false, "extra": "..." }`, temperature 0. `supported: false` is `unsupported-statement`; an unparsable or empty answer is `judge-unparsable`; any caller error (including a guard refusal) is `judge-error`: all of them fail the draft.
`node judge.js --calibrate --models a,b,c [--out file]` measures it: for 14 real ideas a good case (the claim sentences verbatim, nothing added; expected pass) and one bad case per injected defect (event, judgement, recommendation, cause, two figures swapped, an added place or actor, a first-person presence the regex misses, a sea remark the regex misses; fixed sentences in `DEFECTS`). It reports, per installed model, good cases passed, bad cases failed per defect type, misses (with the judged sentence), unparsable answers, caller errors and seconds, and names the model with the fewest misses. The labels come from how the cases are built, not from a person, and the good cases are verbatim: this is a measurement of what the judge catches, not proof that a draft is true. `node judge.js --compare-prompts` runs the caption model with both caption prompts (`PROMPT_V1`, `PROMPT_V2`) on the same ideas and judges every draft that passes.

## Clip library (`clip-library.js`)
The automatic lane only uses clips of a private library (outside every repository, default `~/Movies/Beyond Paradise/clip-library`, override `BPA_CLIP_LIBRARY`). The build cuts short silent vertical clips from the footage catalogue; a clip often holds TWO shots cut together (a lion for three seconds, then elephants), and a headline about elephants must never run over a lion. So a reviewer looks at every clip, at four frames a second, and a clip only reaches the lane when it is ONE shot with ONE clearly identifiable subject.
What the reviewer must look at, for every clip and every child: no person anywhere (not even small or far away), no text or logo, no vehicle, no building; it is one shot, with no cut, dissolve, blend or flash inside; the subject is clearly identifiable the whole time (the animal can be named from every frame). Notes record the reason only and never describe a person. A pass counts only when every frame was read at 400 pixels wide or more: on 17 Nov 2026 a first look at frames about 120 pixels wide passed 18 clips, and a second look at 400 pixels failed 4 of them (a person, vehicles, roofs, a footpath). A small overview sheet may only be used to throw a clip out, never to pass one.
The commands, in this order:
1. `node clip-library.js --build` renders the clips without any text and runs the render and flash checks.
   A build never destroys a judgement: a clip with a verdict, a `shows` record, children, or that is a split child is never rendered over, changed or dropped, even when the plan gives it another span or no longer plans it (it is listed, and the build prints "N judged clips were planned differently and were kept as they are: <ids>" every time; that is the guard working, not a failure, so the exit code stays 0; exit 5 is for render and flash failures only). Run `node clip-library.js --build --dry-run` first: it prints the same counts and renders and writes nothing.
   A judged clip is frozen for the build: its flash check, duration and subject are no longer refreshed, so a judged clip without a flash record stays not eligible until it is judged again.
2. The reviewer looks at each clip.
3. `node clip-library.js --split <id> <cuts> --by <text> [--notes <text>]` for a clip that holds more than one shot. `<cuts>` are boundaries in seconds within the clip, comma separated: a point (`2.9`) drops 0.2 s on each side, a range (`3.25-4.25`) is dropped as given (for a dissolve or a blend). Every remaining piece of at least `MIN_SHOT_SEC` (3 s) becomes a child `<id>-s1`, `<id>-s2` ..., re-encoded from the parent's file (frame exact, no audio, the library's codec settings). A child carries `parent`, its own duration, its source range narrowed to the part it was cut from (so the usage ledger blocks the same footage but not a sibling with a different range), its own render and flash check, and NO verdict and NO tags. The parent is marked `supersededBy` and is never offered again. Refused with exit 2, nothing written and no file left behind: an unknown clip, a clip already split or itself a child, a boundary outside the clip, unordered or overlapping boundaries, no piece long enough, a missing `--by`. A piece that is too short is dropped and reported.
   Write every second with a decimal point; `2,9` is refused as a probable comma decimal, two separate points are written `2.0,9.0`, and two neighbouring points closer than 0.5 s are refused. The planned pieces are printed before anything is written. Child files left by a crashed run (not in the manifest) are replaced. A later `--build` never drops a child or a split parent: children keep their verdicts and tags, and a split parent whose footage the new plan changes is left as it is with a message (exit 5) for the reviewer to decide.
4. The reviewer looks at each child.
5. `node clip-library.js --verdict <id> pass|fail --by <text> [--notes <text>] [--single-subject yes|no]`. `--single-subject yes` means "one shot, one clearly identifiable subject for the whole clip". A clip is eligible for the automatic lane only when its verdict is `pass` AND `singleSubject` is recorded as `yes`; a clip without the field (every clip judged before this rule) is NOT eligible. Judging a clip again replaces the whole record, so repeat `--single-subject`.
6. `node clip-library.js --shows <id> <tag,tag> --by <text>` records what the clip shows (the animal tags the lane pairs on, see below).
`node clip-library.js --summary` lists every clip, children under their parent, and for each clip without a verdict, without the single-subject answer or without tags says what is missing. The shortest clip the render check and the reel QA of the composed video accept is `LIBRARY_CLIP_MIN_SEC` (`reel-clip.js`, equal to `MIN_SHOT_SEC`, a tolerance of 0.1 s for the re-encode); the build itself still plans 6 to 9 s clips, a split makes them shorter. The text band over a clip is static for the whole clip, so a 3 s clip has no hook that appears late; a long hook is simply on screen for 3 s.

## Automatic lane (`auto-lane.js`, `fact-post.js`, `overlay.js`, `overlay.py`)
OFF until config.json says exactly `"autoPublish": true`. The owner allowed automatic publishing on Instagram for ONE class of post only, and these are its rules in plain sentences.
- The text is never written by a model. It is the idea's own title (cut cleanly to at most 60 characters), the idea's own sourced claim sentences word for word (at most 3, each at most 240 characters, never shortened), and the lines code adds (source line, pointer to the site, hashtags). A title that cannot be cut cleanly or a claim that is too long refuses the idea.
- Only ideas of the kinds in `autoKinds` (default rule and fact) that are not in the history, and only when the real final check (voice linter and the owner's content rules) and the deterministic judge checks pass. No question is asked of any model.
- A fact only goes over footage that fits it. The animal an idea is about is the FIRST animal its title or claims name (word table in `auto-pairing.js`; whole words, so "lionfish" is not a lion; a place name that contains an animal word counts as that animal, an accepted limit; "big five" names no animal). A clip fits only when a reviewer recorded that animal among what it shows: `node clip-library.js --shows <clip id> <tag,tag> --by <text> [--notes <text>]` (tags: lion, elephant, buffalo, zebra, hippo, wildebeest, crocodile, bird, giraffe, cheetah, leopard, hyena, rhino, wild-dog and the scene tags savanna, wetland, river, river-crossing, volcano, landscape; an unknown tag, an empty list or a missing `--by` exits 2 and writes nothing; `--summary` lists the tags). Scene tags never match by themselves, the manifest field `subject` is never read, and a clip without `shows` fits nothing. Animals no tag covers (baboon, flamingo, whale shark ...) never fit, which blocks a wrong pairing. The test runs before the text checks: an idea with no animal is refused `no-subject`, one with no fitting unused clip `no-matching-clip`, and only ideas that have a fitting clip count against the 15 tried per run. Every automatic reel carries the code-added line `Video: library footage.` right after the source line (the clips come from compilation videos, so the place of filming is not known); it is part of the hashed text. A title with markup (`*`, backticks, a markdown link, emphasis underscores) is refused as a hook (`title-has-markup`), and a cut title never ends on has, have, had, will, can, that, which or who. The alt text is built from the clip's tags ("Short silent video of a lion and elephants with the text: ...").
- A hand-written hook may replace the title hook: `node auto-hooks.js --add <ideaId> "<hook>"` (checked like the on-video text: at most 60 characters, figures only from the claims, final check; written UNAPPROVED), `--approve <ideaId> --by <text>`, `--list` (approved, unapproved, stale). The lane reads the private file `~/.matlai/bpa-auto-hooks.json` (see "Review page" below); the committed `auto-hooks.json` is only the empty default. An entry belongs to one idea: it matches on `ideaId` only, and `claimsSha256` is the hash of the idea's TITLE and claim texts in order. The lane uses an entry only when it is approved AND the hash still matches (a renamed idea or changed claims make it stale; stale and unapproved entries are ignored). The hook then goes through every check a title hook does, and a hook that names an animal must name the idea's own animal (else `hook-subject-mismatch`, also in `--add`). `node auto-lane.js --rehearse --include-unapproved` previews a current but not yet approved hook (each such block starts with `PREVIEW: hook not approved yet`); only the rehearsal command can do this, never the worker or a config key. A missing or malformed file refuses the lane (`bad-hooks-file`), it never silently falls back to titles. `autoRequireApprovedHook: true` makes an approved hook mandatory.
- A fact whose title (the record's claim sentence) and claim text (its short value) are two different strings carries `titleFromOtherField` and is refused before pairing with `title-claim-differ`, even with an approved hook, because the video could say the opposite of the caption; the approval lane still offers it, where a person reads the draft.
- The footage is only a clip from the private clip library that passed the dense look and the flash check, has the reviewer's `singleSubject: yes` (one shot, one clearly identifiable subject), is not superseded by children and is not in the usage ledger. No clip left means no post that day: there is no other footage and no text-only reel. The hook is laid over the clip by `overlay.py` and one ffmpeg `overlay` command; the render checks must pass.
- At most one a day. Once per East Africa day the worker (after its normal work) prepares one item, only when the stop flag is clear and no Instagram reservation exists for today. The item goes into the queue for `autoSlotHourEAT` (Instagram only, no Facebook leg) and is published by the EXISTING worker path: stop check, final check on the exact text again, cap reservation, claim, host, publish. Any edit of the queued text, on-video text or claims afterwards blocks it (rule id `auto-text-changed`), and so does any refused wording.
- After a successful publish the clip goes into the usage ledger and one WhatsApp line says what went out and how to stop it. When nothing could be prepared, one line a day says why ("No automatic post today: ...").
- Switch-on: edit `autoPublish` in config.json, then restart the approval server (it reads config.json once, at start; the worker is a fresh process each run and sees the change within 15 minutes). The worker writes `bpa-social-armed.json` in the state folder on its first run with the lane on and removes it on any run with the lane off; it is the only writer. If it cannot write it, that run ends in an error (the `worker-failing` alarm). Lane on and no stamp is the health problem `armed-missing`, held back for 20 minutes after the approval server starts, so the switch-on above raises no alarm, while a stamp that never appears does within about an hour.
- Switch-off: edit `autoPublish` out of config.json (or set it to anything but `true`), then restart the approval server the same way. Without the restart the server still believes the lane is on; the worker removes the stamp on its next run, and `armed-missing` would alarm after the 20-minute grace.
- With the lane on, a stamp the worker cannot write (read-only or missing state folder) ends that run in an error BEFORE any queue work: reconciliation with Meta and draft expiry wait too, until the folder is fixed. This is on purpose: the no-post alarm has no clock without the stamp, and the `worker-failing` alarm reports it. With the lane off, a leftover stamp that cannot be removed only logs one line and the run goes on.
- `bpa stop` (or the fleet stop flag) halts it. Turning `autoPublish` off while an item waits holds that item; it stays queued.
- `node auto-lane.js --rehearse [--count 1] [--out dir]` runs that many full preparations (each with its own clip and its own idea) against the real pool and library and writes one video and one caption file per post to the folder; it queues, hosts and posts nothing. `node auto-lane.js --supply [--top 30]` counts how many of the top ideas survive the text checks, by refusal reason, how many of those have a fitting unused clip, and per eligible clip its tags and how many surviving ideas fit it.

## Content rules and the final check (`rules-gate.js`)
`rulesGate(text, { neverPromotePatterns, claims })` is a pure check of the owner's content rules; each violation carries a rule id: `sea-conditions` (seaweed, sea state, waves, swim conditions), `seaweed-farming-place` (farming or harvesting only with Paje, Jambiani or Bwejuu named and none of Michamvi, Pingwe, Kae), `first-person-visit` ("we stayed", "our visit"), `never-promote`, `paid-link-wording` ("book now", "affiliate", "discount code" ...; a plain "more on the site, link in profile" is fine) and `unsourced-figure` (a money amount must appear in a claim `{ text, sourceDate }` that has a date; drafts without claims pass `[]`). Taste and hype stay with the voice linter.
The never-promote list is private: `~/.matlai/bpa-never-promote.json` (`{ "patterns": [...] }`, override `BPA_NEVER_PROMOTE_FILE`), literal case-insensitive whole-word match, never printed, a violation names the pattern's index. A missing, unreadable, empty or malformed file refuses every text (`never-promote-list-unavailable`).
It runs right after the voice gate on every path to the queue (drafting, `bpa edit`, carousel slides) and again as `finalCheck(draft)` (voice gate + rules on the caption, every slide and the on-video text) in the worker before the Instagram publish and in the approval server before `bpa approve` schedules and before `bpa post ... now`, always BEFORE the daily-cap reservation. A failing final check publishes and schedules nothing, sets the item to `blocked` (rule ids in `blocked.rules`; shown by `bpa` and `bpa status`; never retried automatically), writes one log line and sends one WhatsApp alert with the rule ids only. A Facebook post already scheduled at Meta is not cancelled by this; the alert says so.
`node rules-gate.js --check-queue [queue.json]` is read-only: counts per state, and the ids and rule ids of unposted items that would be refused (no text).

## Draft score (advisory)
`score.js` gives every new draft a `score` shown under it in `bpa` / `bpa approve` lists: `score 72/100 · hook 7/10 · rubric 6/9 ✗ cta, hashtags`.
Total = 60% rubric pass-rate + 40% hook score. The 12-part rubric has 9 post-level checks (hook window, concrete hook, one ask, 3-5 hashtags,
brand/links, no slop, concrete fact, readability, length) and 3 profile-level parts (bio, highlights, grid) that are judged monthly and excluded.
It is advisory only: it never blocks, edits or re-statuses a draft, and it does not predict reach. Pattern from Jakeschincariol/Instagram-agent-skill (MIT).

## Approval endpoint authentication
`POST /bpa/action` requires `BPA_APPROVAL_TOKEN` (set it for the approval server and send the same value as an `x-bpa-token` header from the WhatsApp bridge, with `content-type: application/json`). Unset = every action returns 503 (fail closed). The alert number comes from `WHATSAPP_ALERT_TO` first, then from the first line of the private file `~/.matlai/whatsapp-alert-to` (override the path with `WHATSAPP_ALERT_TO_FILE`; the line must look like `+` and 8 to 15 digits). It is never stored in the repo; with neither, alerts are skipped (fail closed) and the log says so. When the file is used because the variable is missing, the log says that once per process.

## Review page (step 2: decide)
A page where the owner looks at video texts and clips, one card at a time, and decides. A video text card has Approve, Skip and Edit; a clip card has Approve and Skip. Edit shows a box; Save runs the same checks as the command line, and when they pass the new text is approved in the same tap. Under "What I decided" every decision of the last 30 days is listed with an Undo button. On a PC the keys A, S and E work. A "Stop all posting" button (two taps) stops posting, and the same button allows it again. The page cannot switch the automatic posting on: no route writes `config.json`. It never calls an AI model and makes no outside request.

- **Open it** from one of the owner's own devices, with Tailscale switched on: `https://<tailnet name>:10000/review/`. Nobody else can reach it, and it is never on the internet.
- **Private settings file** `~/.matlai/bpa-review-access.json`, for example `{ "ownerLogin": "owner@example.com", "host": "device.example.ts.net:10000" }`. Mode 600. Never commit it. It is refused (the page answers "not available") when other users on the Mac can read it, when it is missing, or when it is malformed. It is read on every request, so an edit needs no restart.
- **Access rule.** Every `/review` route needs the owner's Tailscale login in the request, the right host name, and (except the page itself) the session cookie that the page sets. The cookie lasts 12 hours and is only sent to `/review`. Any failure answers the plain text `not available` and logs a reason code, never a header value.
- **Hooks file.** The lane and the page read `~/.matlai/bpa-auto-hooks.json` (private, mode 600). The committed `auto-hooks.json` stays as the empty default. Run once: `node auto-hooks.js --migrate <hooks file>` (it never overwrites an entry for the same idea and writes nothing when anything is unusable). The lane and the page refuse the file when other users can read it or when it is not a regular file. Until that file exists the lane refuses (`bad-hooks-file`).
- **Publish it on the tailnet:** `tailscale serve --bg --https=10000 http://127.0.0.1:3028`. Never use Tailscale Funnel for this page. Remove it with `tailscale serve --https=10000 off`.
- **Old routes stay loopback only.** `POST /bpa/action` (token) and `GET /health` on loopback work as before for the WhatsApp bridge and the worker. Because `tailscale serve` publishes the whole port, both now refuse any request that carries `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto` or a `Tailscale-*` header (a request through the published port always does; a loopback caller never does). Through the published port `/health` needs login and cookie.
- **Sessions.** At most one new session cookie per 2 seconds, a session younger than 60 seconds is never dropped, at most 50 at a time; a page load without a cookie that is too soon answers 429 `not available`. A session is only issued to a real page load (browser navigation, or the page's own `X-Bpa-Page: 1` request header); any other cookie-less request to the page (an image tag or a background request from another website open in the same browser) is refused `not available` and uses up nothing.

- **Private files written by step 2** (all in the state folder, mode 600, never committed): `bpa-clip-approvals.json` (the clip decisions), `bpa-review-decisions.jsonl` (the decision record, one line per decision, no texts), and the lock `bpa-decisions.lock` (one lock for every writer). The hooks file `bpa-auto-hooks.json` gains the state "skipped".
- **What each route needs.** `GET /review/` is the only route that issues a session cookie, and only to a real page load (navigation, or the page's own `X-Bpa-Page: 1` request header). `POST /review/api/session` needs login, host, a valid cookie and that header; it issues no cookie and hands out the action token only to a request that already has a valid cookie. `POST /review/api/decide` and `POST /review/api/posting` need login, host, a valid cookie, the action token in `X-Bpa-Action`, the content type `application/json` and a body of at most 2048 bytes. Every guard failure answers the plain text `not available`; after the guards a refusal answers 409 with a short code that the page turns into one plain sentence.
- **Every decision is checked against what the owner saw.** The page sends the version of the card; if the facts, the clip file or the tags changed since, the decision is refused and the card reloads. The decision is written to the record first and to the state file second; if either fails, nothing counts. Approve of a video text runs its checks again right then; Approve of a clip needs it to be ready right then.
- **Hardening after the reviews.** Every state-changing request (`session`, `decide`, `posting`) is refused with `not available` when it carries `Sec-Fetch-Site` and that value is not `same-origin`; the page load is exempt, because opening the page from a link in a chat app is a cross-site navigation. Approve of a video text runs its checks before it takes the decision lock and re-checks the state, the version and the facts under the lock, so a slow check never makes another decision wait. The edit box refuses control, format, private-use and unassigned characters, line and paragraph separators, every space except the plain one, variation selectors and the fillers that draw nothing (the page and the server hold the same set). The Stop and Start lines of the decision record are written under the same lock as every other line. A torn last line in the record (a crash in the middle of a write) is moved to `bpa-review-decisions.jsonl.torn`, the next record starts after the last good line, and one code is logged; a damaged line anywhere else still stops every decision. Start carries the stop the page showed; if posting was stopped again in between, it is refused (`stop-changed`) and the owner taps again. A clip file that is a symbolic link counts for nothing.
- **What the character rule depends on.** The rule "unassigned character" (Unicode category Cn) depends on the Unicode version of the server's Node and of the owner's browser, so a newly assigned character can pass on one side and be refused on the other; the server is the authority, and a text the page lets through can still be refused with `bad-characters`. An emoji joined with a variation selector or a zero-width joiner is refused in a hook text on purpose.
- **One-way clip rule.** The first time every clip the lane could take today has a decision, the lane switches to "approved clips only" for good (`enforcedAt` is recorded and never cleared). Before that, undecided clips are used as before; a skipped clip is never used. Undoing a decision keeps the lane strict.
- **30 days.** A decision older than 30 days leaves the page, and its clip leaves the list of viewable videos, but it stays in force for the lane.
- **Undo** works on the current state: an approved or skipped video text or clip that is unchanged and not yet used in a post. Undo of an edit-and-approve unapproves the new text (it goes back to waiting); the old text is not restored.
- **`--summary` of the clip library** counts clips by the library rules only; it does not apply your Approve and Skip decisions.
- **Who acted.** The login in the decision record is the one the proxy header claimed; it is not proof of who acted. The boundary is the Mac user account: a program of that user can obtain a cookie and a token with forged headers, and can edit the state files anyway.
- **Undo the whole step.** `git revert` of the merge and restart the approval server. The private files can stay.

### Step 3: drafts and prepared posts

The page now also shows the drafts in the queue (card kind "Post") and the posts the automatic lane has prepared. A draft card shows the whole text (several lines are kept as written), the recorded facts and sources, the day it must be decided by, the next free day, and a plain reason when it is not ready.

- **Approve schedules a real post.** It makes a real Facebook post at Meta for the next free 09:00 East Africa time, and adds the Instagram leg when Instagram is on. The page asks a second question first (the "Schedule it" button) and names the day; the box is bound to the card and the day it showed, and sends nothing if either changed. It cannot be undone here. Only Meta can cancel it, in Meta itself. A key never approves or skips a post.
- **Skip is final.** The draft does not come back on this page. There is no Undo for drafts, because the engine has none.
- **Edit does not approve.** It saves the new text and removes the recorded sources, so a text with numbers or places needs its sources recorded again (the page cannot record sources). A new number must be one of the draft's own facts: this check runs on the page and on the WhatsApp command alike.
- **Automatic posts are read only.** The page shows the text and the prepared video, with the large Play button. Stop all posting holds them. Nothing here can approve or change them.
- **Size limit.** A request body may be at most 2048 bytes. A longer edit is refused on the page before it is sent, with the words "too long to save from this page".
- **Locks.** The queue lock is taken first, and the call to Meta happens under it. The decision record is written under the decision lock, only for the short record line. A hook or clip decision is never blocked by a slow Meta call, and a call that hangs is stopped after 70 seconds.
- **After an unknown outcome: check Meta first, on both routes.** If Meta did not answer in time, answered with an error, or the page could not save after Meta said yes, the draft is marked and answers `check-meta` from then on, to the page, to `bpa approve B1` and to `bpa post B1 now` alike. A failure of `bpa approve` on WhatsApp sets the same mark, so the page then refuses too. The only exception is the stop refusal, because nothing reached Meta. Look in Meta before doing anything else. If no post is there, send `bpa approve B1 again` on WhatsApp (or `bpa post B1 now again` if the failed try was a post now): it clears the mark, writes one log line (the words `approve again` or `post now again` and the id, no text) and then runs the normal command with every guard. On a draft without the mark both answer `nothing to repeat`. The mark is written to the queue file BEFORE the call to Meta, on every route (scheduling from the page, `bpa approve`, `bpa post B1 now`): if the service dies during the call, or a save after a good call fails, the mark is already on disk and a plain retry is refused. A stop refusal removes the mark again, because nothing reached Meta. If the queue cannot be saved before the call, nothing is sent (the page answers `write-failed`). The page has no such override, and its record line for the earlier try stays, so the page keeps answering `check-meta` for that draft. `schedule-not-saved` means the post was scheduled but the page could not save that: check Meta before tapping again.
- **What the card does not offer.** A text longer than 5,000 characters (more than the card can show) has no Approve and no Edit and is refused with `text-too-long`: decide it on WhatsApp. A draft whose creation time cannot be read counts as expired on the page. A draft made by the automatic lane has no Edit on the page (an edit would make its own text check hold it back for good). Hidden characters in a slide text refuse Approve like those in the caption. The edit counter shows the real ceiling, about 1,900 characters, because the request is limited in bytes.
- **The date the owner confirmed is the date that is scheduled.** The request carries the day the card showed. If another post took that day in the meantime, the request is refused and the card reloads.
- **Where the real scheduling function reaches the page.** In exactly one place: `createDefaultActions` in `review-routes.js`. The review handler has no default actions, and `approval-server.js` passes the real ones explicitly. A static test pins this.
- **Approve for drafts is OFF until the file `bpa-page-approve-on` exists** in the private state folder (mode 600 and owned by the account that runs the server; the page cannot create it, only the owner's say-so and the operator can). Delete the file to switch it off again; no restart is needed. While it is off, the card says so, and Skip and Edit still work.
- **The stop flag** file is now written with mode 600. A flag that already exists keeps its mode until Start removes it; the next Stop creates it with 600.
- **Arming Stop.** The first tap of Stop (or Start) arms the button for 5 seconds. If the second tap comes too late, the page now says so in a sentence.
- **Undo the step.** `git revert` of the merge and restart the approval server. No private file needs to change.

## YouTube channel editor: explicit decisions (`youtube-channel-edit.js`)
`plan --out <dir>` builds the rule-based description clean-up. `plan --out <dir> --decisions <file.json>` builds the plan ONLY from that file: the text rules are not run, so a decisions plan can never re-apply rule changes. `apply` and `undo` are unchanged in shape (`apply --plan <plan.json> --ledger <dir> [--only id,...] [--max-units N]`, `undo --ledger <file> [--only id]`; `--only` takes a video, playlist or channel id, or the `key` of a playlist-create). Nothing is written by `plan`; it reads the live objects and puts old and new values (plan.json) and a readable diff (plan.md) into the plan files.

```json
{ "ops": [
  { "channel": "asia", "kind": "video", "id": "<videoId>", "set": { "title": "...", "description": "..." } },
  { "channel": "asia", "kind": "playlist", "id": "<playlistId>", "set": { "title": "...", "description": "...", "privacyStatus": "private" } },
  { "channel": "asia", "kind": "channel", "id": "<channelId>", "set": { "title": "..." } },
  { "channel": "asia", "kind": "playlist-create", "key": "vietnam", "set": { "title": "...", "description": "...", "privacyStatus": "public" }, "items": ["<videoId>", "<videoId>"] }
] }
```
Fields: video `title`, `description`; playlist `title`, `description`, `privacyStatus`; channel `title`; playlist-create `title`, `description`, `privacyStatus` (required: `title`, `privacyStatus`). Any other key in an op or in the file is refused, so a typo cannot become a write.

**The plan is refused (exit 1, no file written, every refused op named as `decisions op #N`) when:** a field is outside that list; a video title is empty or over 100 characters, a playlist title empty or over 150, a channel title empty or over 100, a description over 5,000 BYTES (UTF-8; 2,400 three-byte characters is too long), a title over its limit counted in code points (an emoji counts once), or any title/description contains `<` or `>`; a playlist `privacyStatus` is not `private` or `public`; an op sets a video's privacy or has kind `delete` (there is no such op); the id does not belong to the named channel or does not exist; a playlist-create item is not a public video of that channel; the text contains `beyondparadiseadventures.net` or a web address (a scheme, `www.`, or a dotted word ending in a lowercase or all-caps top-level domain; "Great.Be careful" and "Day 1.Co-op" are not addresses) whose host is not one of `beyondparadiseadventures.com`, `www.instagram.com`, `www.youtube.com`, `www.facebook.com` (so `www.beyondparadiseadventures.com` and `instagram.com` without `www.` are refused too; write the exact host); two ops name the same object. **Dropped with a note (not refused):** a private video (`private`), a value equal to the live one (`already-applied`; an op that changes only some of its fields keeps just those), a playlist-create whose title already exists on the channel (`already-exists`).

`apply` re-checks the same content rules on every op that sets a title or description, touches privacy, or creates a playlist, whatever its `source` flag says (a hand-edited plan.json cannot get past it; the 60 real rule-plan ops pass), and writes in the usual order: `pending` line with ALL old snippet and status values, the write (video title/description: `videos.update` snippet with the live tags, category and languages unchanged; playlist: snippet and/or status in one call; channel title: the full live `brandingSettings`, banner untouched), read-back with the existing retries, result line. The read-back also asserts tags, category and privacy did not change. A channel title is never believed from the write's own answer: it is always read back live with the retries. A rename that YouTube answers with HTTP 400, or 403 with a title-specific reason, or whose read-back still shows the old title after all retries, is ledgered `refused-by-youtube` and the run continues. 401, 429, any reason containing quota / rateLimit / authError / insufficientPermissions, the plain reason `forbidden`, and every other mismatch or error stop the run.

**Creating a playlist** is private-first, so a half-built playlist is never visible. It is ALWAYS inserted `private`, the items are added, and only after every item has its ledger line is the requested privacy set (one `playlists.update` part status, read back). Cost: 50 units for the insert, 50 per item, 50 for the privacy update (not when `private` was requested), all paid for against `--max-units` before it starts. Ledger lines: `pending`, `created` (the new playlist id), one `item-created` per item (the playlistItem id), `privacy-pending`, `privacy-done`, `done`. **Re-run rules** (looked up in all `changes-*.jsonl` of the ledger folder): a same-title playlist plus a `done` line for the key = `already-applied`; a same-title playlist plus a `created` line with that playlist id but no `done` = RESUME (the playlist's items are listed, only the missing ones are inserted in order, then the privacy, then `done`; extra items this ledger never inserted stop it); a same-title playlist this ledger did not create = stop with `playlist-exists-not-ours` (names the id; it is never adopted, changed or deleted; look in YouTube Studio). If an insert's response is lost the playlist exists but is private, and the re-run stops with that message.

**Undo** puts title, description and privacy back from the `pending` line (also when the run died before the result line). A created playlist is undone by `playlists.delete` of the id recorded on a `created` line **of the same ledger file for that same attempt and channel**, and only if the playlist still has the title this tool gave it, holds only items this ledger inserted, and is private or has the planned privacy; any other id is never deleted. A `pending` playlist-create whose insert response was never recorded does nothing and prints where to look by hand. Undo refuses ledger lines that list a field outside `ALLOWED` (for example a video's privacy).

**Real-API notes (from the first live run).** Every `playlists.update` (privacy-only, title/description, the final privacy step of a create, undo) is sent as `part=snippet,status` with the full live snippet and the status, because the API rejects an update without `snippet.title` (answer: HTTP 400 `{0}`). Each apply run writes its own ledger file `changes-YYYY-MM-DD-HHMMSS.jsonl` (a `_n` suffix if the same second is taken), so undo of a later run never reverts an earlier one; older `changes-YYYY-MM-DD.jsonl` files stay readable, and re-run rules still look in every `changes-*.jsonl`. A failed op prints the response body's error reasons (`[reason: ...]`) and stores them on the `failed` line. Top-level domains that are never ordinary words (com, net, org, io, ly, vn, tz, uk, eu, biz, xyz, ae, fr, nl, tv, de) are matched in any case; English-word ones (be, me, co, us, app, info, shop, blog, site, online, travel, asia, africa) only in lowercase or ALL CAPS.

## Own Instagram results and unanswered comments (read only)
`node insights.js --fetch [--force]` reads the account's media list and per-media reach, saved, shares, views and total interactions (a metric the API refuses for one media is recorded as absent) into `bpa-ig-insights.json` in the state folder (mode 600, no caption text, only its hash; `queueId` when the permalink or media id matches a `queue.json` item). One real fetch per East Africa day unless `--force`; an API error names its reason and writes nothing. `node insights.js --summary` prints counts and median reach by product type, weekday and month plus the ten best and weakest by reach. `ideas.js` uses the file as a bounded nudge: with 4 or more of our own posts of a topic and a state not older than 14 days, the topic median reach against the account median moves an idea's score by at most +-5 and adds a line to its `reasons`; otherwise nothing changes.
`node comments.js --fetch | --list [--questions] | --count` keeps `bpa-ig-comments.json` (mode 600): top-level comments with no reply from our own account, newest 60 media. Texts and names live only in that file and in the terminal output of `--list`; nothing else prints them. Both tools only send GET requests to the Graph API host (guard: `assertReadOnlySpec`); neither can reply, like, hide or delete.
